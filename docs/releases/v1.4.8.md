# v1.4.8 — stale LVM signature hotfix

`obj08-09` reached the intended `lvcreate` task after the timeout-containment
fix, then failed immediately because the newly allocated LV exposed an old XFS
signature left in reused physical extents.

This is expected storage behavior: recreating the partition/PV/VG metadata does
not zero every data extent. LVM therefore detected the old XFS signature and,
in a non-interactive Ansible execution, refused the default answer to the
signature-wipe prompt.

v1.4.8 makes training automation deterministic:

- setup-side `lvcreate` commands use `--yes --wipesignatures y`;
- QA reference `lvcreate` commands use the same non-interactive contract;
- normal OBJ08 reset wipes signatures from known training LVs before removing
  them, reducing stale data carried into later runs;
- a release gate prevents future automated `lvcreate` paths from reintroducing
  interactive stale-signature prompts.

The student-facing storage skill remains unchanged. The automation only
removes an unintended prompt from lab preparation and QA execution.
